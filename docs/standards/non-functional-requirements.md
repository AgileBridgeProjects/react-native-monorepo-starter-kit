# Non-Functional Requirements — The Law

These requirements apply to every layer of the StarterKit stack (mobile, web, backend).
They are non-negotiable and must be considered in every design decision, code review, and
new-feature implementation — whether written by a human or generated by an AI tool.

Implementation playbooks for each area live alongside this file:

- Security: `docs/standards/nfr-security.md`
- Accessibility: `docs/standards/nfr-accessibility.md`
- Compliance (POPIA/GDPR): `docs/standards/nfr-compliance.md`
- Performance: `docs/standards/nfr-performance.md`
- Observability: `docs/standards/nfr-observability.md`

---

## Performance & Scalability

- The system must handle **≥ 5 000 concurrent users** without degradation (mobile app + admin web portal combined).
- Capacity planning must accommodate **20% user-growth increments** — design for horizontal scalability from day one.
- **Response-time SLO**: all critical user actions (login, data fetch, game launch) must complete in **< 2 seconds** under normal load (p95).
- Mobile apps must deliver smooth animations and transitions (≥ 60 fps) on all supported devices.
- Backend services must be stateless and deployable behind a load balancer — no sticky-session requirements.
- N+1 queries are a bug, not a code smell. Every list endpoint must have covering indexes and pagination.
- List endpoints must never return unbounded arrays — mandatory `pageSize` with a cap of 100.

**AI enforcement rule:** when implementing a new endpoint or screen, flag any design that prevents
horizontal scaling (in-process caches keyed by user session, blocking synchronous calls without
timeout, missing pagination on list queries). Flag any `IEnumerable` returned directly from EF Core
without `.Take()` / pagination.

See `docs/standards/nfr-performance.md` for Polly retry pipelines, EF Core tuning, React Query
`staleTime` recommendations, `FlashList` usage, and 60-fps animation patterns.

## Availability & Reliability

- **Uptime target**: 99.9% for web and mobile applications, excluding planned maintenance windows and upstream-provider outages (Firebase Auth, Azure B2C, AI providers).
- All calls to external dependencies (HTTP, SQL, AI providers) must use retry policies with exponential back-off and jitter.
- Background jobs (Hangfire) must always reach a terminal state (`Completed` or `Failed`) — never stay stuck in `Running` after a crash. See `[AutomaticRetry(Attempts = 0)]` rule in `docs/standards/backend.md`.
- Critical user data must be persisted durably; use database transactions or idempotency keys for in-flight writes.
- Every API service must expose `/health` (liveness) and `/health/ready` (readiness) endpoints.

**AI enforcement rule:** every new service method that calls an external dependency must include a
resilience pipeline (retry + circuit breaker). A method that calls `HttpClient` or a repository
without a Polly pipeline is incomplete.

## Security

- **All data in transit must be encrypted with TLS 1.2 minimum; TLS 1.3 is the required default.**
- HTTP is forbidden in production — all API traffic must go over HTTPS.
- Sensitive personal data must be encrypted at rest using AES-256 or equivalent. Storage-level encryption at rest (enabled by default on Azure Database for PostgreSQL Flexible Server) must be active on all production databases.
- No secrets (API keys, connection strings, certificates) may be stored in source control. Use Azure Key Vault / EAS Secrets for runtime injection.
- RBAC must be enforced in the backend — never rely on frontend gating alone.
- Every protected API endpoint must be tested with both an authenticated request (200/201) and an unauthenticated request (401).
- Adhere to OWASP Top 10: parameterised SQL (EF Core), sanitised HTML rendering, SSRF guard on URL-fetching endpoints, IDOR ownership checks.

**AI enforcement rule:** flag any code that stores auth tokens in `AsyncStorage` (mobile) or
`localStorage` (web), uses a plain HTTP URL for API calls, constructs raw SQL strings, calls
external URLs without an SSRF guard, or exposes secrets in code or config files.

See `docs/standards/nfr-security.md` for TLS config snippets, secrets management patterns,
token storage, RBAC setup, and security headers.

## Compliance — POPIA & GDPR

> South African POPIA is the primary compliance obligation. GDPR alignment is required for any EU user data.

- Collect only the personal information strictly necessary for each feature's purpose (data minimisation).
- Users must give informed, explicit consent before personal data is collected or processed.
- The backend must support data-subject rights: **access** (export all PII), **rectification** (update), and **erasure** (right to be forgotten with cascade).
- PII must never appear in log output — redact before writing to any log sink.
- Define and enforce data-retention policies; automate purging of expired records.
- A documented incident-response procedure must be maintained; regulatory breach notification under POPIA is 72 hours.

**AI enforcement rule:** when adding a database column that holds personal information (name, email,
phone, national ID, location, IP address), the PR must include: justification for the data being
collected, erasure cascade handling, and a log-redaction update. Flag any `_logger.Log*` call that
could include PII fields.

See `docs/standards/nfr-compliance.md` for data-classification guidance, consent flow patterns,
erasure endpoint implementation, PII redaction in Serilog, and the breach-response runbook.

## Usability & Accessibility — WCAG 2.1 AA

### Web (`apps/web` — Next.js)

- All interactive elements must be keyboard-navigable and have visible focus indicators (`focus-visible` Tailwind class).
- Images must have meaningful `alt` text; decorative images use `alt=""`.
- Colour contrast ratio must meet AA: **≥ 4.5:1** for normal text, **≥ 3:1** for large text (18px+ or 14px bold+).
- Every `<input>` must have an associated `<label>`; error messages must be linked via `aria-describedby`.
- Dynamic content updates (toasts, modal dialogs, live regions) must use `aria-live="polite"`.

### Mobile (`apps/expo` — React Native)

- Every interactive component must declare `accessible={true}`, `accessibilityLabel`, and `accessibilityRole`.
- `accessibilityHint` must describe the result of activating a control when it is not self-evident from the label.
- Information must never be conveyed by colour alone — pair colour cues with icons, text, or patterns.
- Touch targets must be **≥ 44 × 44 dp**.
- `allowFontScaling={false}` is forbidden — always support system Dynamic Type / font-size settings.

**AI enforcement rule:** every new screen or reusable component must include the appropriate
accessibility props. A component without `accessibilityLabel` on its interactive elements is
incomplete. Flag `allowFontScaling={false}` and hardcoded `fontSize` values not coming from
design tokens.

See `docs/standards/nfr-accessibility.md` for per-component checklists, focus-trap patterns,
VoiceOver/TalkBack testing guide, and contrast-checking workflow.

## Compatibility

### Web browsers

Chrome, Edge, Safari, Firefox — latest two major versions. IE is not supported.

### Mobile platforms

| Platform | Minimum version | Notes |
|---|---|---|
| iOS | 15.1 | App Transport Security enforces HTTPS |
| Android | 7.0 (API 24) | Network security config enforces HTTPS |
| HarmonyOS (Huawei) | 3.0+ / EMUI 11+ | Requires HMS adapter layer — see note below |

### Huawei / HarmonyOS support

Post-2019 Huawei devices do not include Google Mobile Services (GMS). Supporting them requires:

1. Replace FCM push notifications with **HMS Push Kit** (or a dual-delivery abstraction layer).
2. Replace Google Maps with **HMS Map Kit** if maps are used.
3. Replace Google Sign-In with **Huawei ID** or another OAuth provider.
4. Distribute via **Huawei AppGallery** (separate from Google Play).

**Recommended approach:** a platform-detection abstraction — one codebase with HMS/GMS adapters
selected at runtime via `isGmsAvailable()` / `isHmsAvailable()`. This is a dedicated spec task;
do not add HMS adapters inline without an approved spec.

### Graceful degradation

Unsupported OS versions must display a clear upgrade prompt — not crash silently.

## Offline & Data Efficiency

- Core features (viewing previously loaded content, drafting) must function in offline/low-connectivity mode where technically feasible.
- React Query `staleTime` and `gcTime` must be explicitly set per resource type — do not rely on library defaults for production queries.
- Remote images must use `expo-image` with `cachePolicy="memory-disk"` — never the bare React Native `<Image>` component for remote URLs.
- API responses that include lists must be paginated (cursor or offset) — never return unbounded arrays.
- HTTP responses must be compressed (gzip / Brotli on the server; `Accept-Encoding: gzip, br` on the Axios client).

## Monitoring & Logging

- All API services must emit structured JSON logs (no plain-text log lines in production).
- Log levels: `Information` (normal flow), `Warning` (recoverable / unexpected), `Error` (exception caught), `Fatal` (startup failure).
- **PII must never appear in log output** — apply a Serilog destructuring policy that replaces known PII property names with `[Redacted]`.
- Centralised log aggregation (Azure Monitor / Application Insights) must be configured for all production services.
- APM must capture request duration, error rates, and dependency call latency.
- Mobile apps must report crashes and non-fatal errors via Sentry or Firebase Crashlytics.
- Required dashboard panels per service: request error rate, p95 response time, background-job failure rate, active user count.

**AI enforcement rule:** flag any `_logger.Log*` call that passes a user-supplied string or known
PII property (email, name, phone, ID number) directly into the message template or as a structured
value without redaction.

See `docs/standards/nfr-observability.md` for Serilog setup, PII destructuring policy, health-check
registration, Sentry integration, and dashboard/alert thresholds.

## Maintainability & Extensibility

- Code must follow the modular feature-slice architecture defined in `docs/standards/architecture.md`.
- New gamification or AI features must be added via the provider/plugin pattern — not by modifying core orchestration logic.
- Every new public API or service method must have corresponding tests before the PR is merged (see `docs/standards/backend.md`).
- Deprecated features must be marked with `[Obsolete]` (C#) or `@deprecated` JSDoc (TypeScript) and removed in the following sprint.

---

## Internationalisation & Localisation (i18n / l10n)

- All user-visible strings must be externalised to translation files — never hardcode UI text in component files.
- Date, time, number, and currency formatting must use `Intl` APIs (web) or `expo-localization` + `Intl.DateTimeFormat` (mobile).
- RTL layout support must be considered for any new component that uses directional layout (`flex-row`, absolute positioning).
- The default locale is `en-ZA`; adding a new locale must require no code changes — only new translation files.

## PR Checklist — NFR Gates

Before marking a PR ready for review, confirm all applicable items:

- [ ] No unbounded list queries (pagination in place, `pageSize` cap enforced)
- [ ] No PII in log statements (redaction policy applied)
- [ ] Retry + circuit-breaker policy on all new external calls
- [ ] Accessibility props on all new interactive UI elements (`accessibilityLabel`, `alt`, `aria-*`)
- [ ] HTTPS-only; no plain HTTP API URLs anywhere in the diff
- [ ] Sensitive data in secure storage (not `AsyncStorage` / `localStorage`)
- [ ] Any new personal-data DB column has: erasure cascade noted, log-redaction update included
- [ ] Tests exist for happy path, auth-failure path (401), and any new service method
- [ ] New endpoint has `/health` or liveness equivalent if it introduces a new service
- [ ] Response compression enabled for new API projects
