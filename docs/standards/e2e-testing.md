# E2E Testing Standards — The Law

All rules in this file govern code in `e2e/`. They are non-negotiable and apply whether
code is written by a human or generated by an AI tool.

---

## Folder Structure

```text
e2e/
  playwright.config.ts          ← unified Playwright config (all projects)
  .env.e2e                      ← E2E credentials (gitignored; never committed)
  playwright/
    global-setup.ts             ← auth + backend health check
    selectors.ts                ← test-id constants (COMPANY_TEST_IDS etc.)
    pages/
      dx-grid.base.ts           ← abstract DxGridPage base class (extend for any grid page)
      <feature>.page.ts         ← Page Object per page
    utils/
      auth.ts                   ← loginAsAdmin helper + env credential constants
      mock-routes.ts            ← fulfillJson, pagedResponse, getPageParams helpers
  tests/
    web/                        ← Admin Portal (Next.js) tests
      <feature>/
        <feature>.spec.ts       ← mocked-API tests (rendering, sorting, pagination)
        <feature>-audit-log.spec.ts  ← cross-feature integration (real backend)
    expo/                       ← Expo mobile tests
```

## Page Object Model (POM) — mandatory

Every page under test **must** have a corresponding Page Object in `playwright/pages/`.

```text
/playwright/pages/<feature>.page.ts   ← POM class
```

### Rules

- **All selectors live in the Page Object** — spec files never hardcode CSS selectors or
  `data-testid` strings directly. They import from the POM.
- **`data-testid` constants** live in `playwright/selectors.ts` as a named export
  (e.g. `COMPANY_TEST_IDS`). The POM imports from there; spec files never import selectors directly.
- **POM methods are awaitable** (`async`), returning `Promise<void>` for actions and `Locator`
  for accessors (getters).
- **Never call `expect` inside a POM** — assertions belong in spec files only.

```typescript
// playwright/selectors.ts
export const COMPANY_TEST_IDS = {
  page: 'companies-page',
  addButton: 'add-company-button',
} as const;

// playwright/pages/companies.page.ts
export class CompaniesPage extends DxGridPage {
  readonly pageContainer: Locator;
  readonly addButton: Locator;

  constructor(page: Page) {
    const pageContainer = page.getByTestId(COMPANY_TEST_IDS.page);
    super(page, pageContainer);
    this.pageContainer = pageContainer;
    this.addButton = page.getByTestId(COMPANY_TEST_IDS.addButton);
  }

  async goto() { await this.page.goto('/companies'); }
}
```

## DxGridPage — abstract base class for grid pages

Every Page Object for a page that contains a DevExtreme DataGrid **must** extend `DxGridPage`
from `playwright/pages/dx-grid.base.ts`.

```typescript
export class CompaniesPage extends DxGridPage {
  constructor(page: Page) {
    const pageContainer = page.getByTestId(COMPANY_TEST_IDS.page);
    super(page, pageContainer);  // ← passes scoped container to base
  }
}
```

The base class provides: `grid`, `columnHeaders`, `dataRows`, `noDataText`, `gridErrorMessage`,
`getColumnHeaders()`, and `waitForGridLoad()`. Do **not** redefine these in subclasses.

Any property or method specific to a single page (e.g. `addButton`, `popup`, `sortCreatedDesc()`)
stays in the subclass.

## Auth in beforeEach — use `loginAsAdmin`

Every `beforeEach` for an authenticated spec **must** call `loginAsAdmin(page)` from
`playwright/utils/auth.ts`. Do **not** inline the login ceremony in each spec file.

```typescript
import { loginAsAdmin } from '../../../playwright/utils/auth';

test.beforeEach(async ({ page }) => {
  await loginAsAdmin(page);
  companiesPage = new CompaniesPage(page);
});
```

`loginAsAdmin` navigates to `/login`, fills credentials from `.env.e2e`, submits, and asserts
the redirect to `/companies`. Credentials are sourced exclusively from environment variables —
never hardcode them in spec files.

## Mock route helpers — `fulfillJson`, `pagedResponse`, `getPageParams`

Import from `playwright/utils/mock-routes.ts`. Do **not** inline `route.fulfill` JSON boilerplate.

### `fulfillJson(route, data, status?)`

Replaces the repeated `route.fulfill({ status, contentType, body: JSON.stringify(…) })` call:

```typescript
// ✅ Use this
await page.route('**/api/companies**', (route) => fulfillJson(route, MOCKED_LIST));

// VIOLATION: do not inline
await page.route('**/api/companies**', (route) =>
  route.fulfill({ status: 200, contentType: 'application/json', body: JSON.stringify(MOCKED_LIST) }),
);
```

### `pagedResponse(items, totalCount, options?)`

Builds the standard `{ items, totalCount, page, pageSize, hasNextPage }` envelope.
Defaults: `page=1`, `pageSize=50`, `hasNextPage=false`.

```typescript
// ✅ Use this
await page.route('**/api/companies**', (route) =>
  fulfillJson(route, pagedResponse(ITEMS, 2)),
);

// Override page/pageSize/hasNextPage when needed
fulfillJson(route, pagedResponse(page2Items, 52, { page: 2, hasNextPage: false }))
```

### `getPageParams(url)`

Extracts `Page`/`page` and `PageSize`/`pageSize` from a URL, handling both capitalised and
lowercase variants from the DX CustomStore:

```typescript
// ✅ Use this in pagination tests
const { page: sentPage, pageSize: sentPageSize } = getPageParams(page2Response.url());
expect(sentPage).toBe('2');
expect(sentPageSize).toBe('50');

// ✅ Use in parametric route handlers instead of manual URL parsing
await page.route('**/api/companies**', (route) => {
  const { page: pageParam } = getPageParams(route.request().url());
  return fulfillJson(
    route,
    pageParam === '2' ? pagedResponse(page2Items, 52, { page: 2 }) : pagedResponse(page1Items, 52, { hasNextPage: true }),
  );
});
```

## Mock versus real backend — clear boundary

| Test type | Uses real backend? | Rationale |
|---|---|---|
| Page rendering | **No — mock** | Column headers, empty state, add button render regardless of DB state |
| Search panel | **No — mock** | Verify DX search triggers a filtered API call; no need for real data |
| Column sorting | **No — mock** | Assert the correct `SortBy`/`SortDescending` params reach the backend |
| Pagination | **No — mock** | Simulate `totalCount > pageSize` with deterministic fixture data |
| CRUD (create/edit/delete) | **Yes — real backend** | Verify persistence end-to-end; cannot be mocked reliably |
| Cross-feature integration | **Yes — real backend** | e.g. Company CRUD → Audit Log; requires DB state from a prior step |

**Violation:**

```typescript
// VIOLATION: mocking in a CRUD test
await page.route('**/api/companies**', ...);  // ← CRUD tests must call the real backend
```

## Mocking with `page.route`

Use `page.route('**/api/<resource>**', ...)` to intercept all variations of the resource URL.
Always use `fulfillJson` and `pagedResponse` from `mock-routes.ts` — never inline the raw
`route.fulfill` shape.

```typescript
// Standard fixture shape for paginated list endpoints
const MOCKED_LIST = pagedResponse(
  [
    { id: 'aaaa-0001', name: 'Acme Corp', createdAt: '2025-01-01T00:00:00Z' },
    { id: 'aaaa-0002', name: 'Beta Ltd',  createdAt: '2025-01-02T00:00:00Z' },
  ],
  2,
);

await page.route('**/api/companies**', (route) => fulfillJson(route, MOCKED_LIST));
```

### Stateful mocks (call-count based)

When a single test needs different responses for the initial load vs a subsequent action
(e.g. search returning a filtered list), use a `callCount` variable:

```typescript
let callCount = 0;
await page.route('**/api/companies**', (route) => {
  callCount++;
  void fulfillJson(route, callCount === 1 ? MOCKED_LIST : FILTERED_LIST);
});
```

### Parametric mocks (URL-based)

When a test needs different responses for different query params (e.g. page 1 vs page 2),
use `getPageParams` to extract pagination params and `fulfillJson` to respond:

```typescript
await page.route('**/api/companies**', (route) => {
  const { page: pageParam } = getPageParams(route.request().url());
  return fulfillJson(
    route,
    pageParam === '2' ? pagedResponse(PAGE2_ITEMS, 52, { page: 2 }) : pagedResponse(PAGE1_ITEMS, 52, { hasNextPage: true }),
  );
});
```

## Waiting for network activity — sequential vs concurrent

### Waiting for a response triggered by a user action (`Promise.all`)

Register `waitForResponse` **before** the action so you never miss a fast response:

```typescript
// ✅ Register waitForResponse FIRST, then trigger the action concurrently
const [createResponse] = await Promise.all([
  page.waitForResponse(
    (resp) =>
      resp.url().includes('/api/companies') &&
      resp.request().method() === 'POST' &&
      resp.status() === 201,
  ),
  companiesPage.fillAndSubmit(uniqueName),
]);
expect(createResponse.ok()).toBe(true);
```

### Sequential sort clicks (exception to the above)

When clicking a column header **twice** to reach a specific sort state, register
`waitForResponse` **after** each click, not before. This prevents the second
`waitForResponse` listener from being triggered by the in-flight response from the
first click before that listener was even ready:

```typescript
// ✅ Sequential: click then wait — safe when the response cannot precede the listener
await createdHeader.click();
await page.waitForResponse(
  (resp) => resp.url().includes('/api/companies') && resp.url().includes('SortBy=createdAt'),
  { timeout: 10_000 },
);
await createdHeader.click();
await page.waitForResponse(
  (resp) =>
    resp.url().includes('/api/companies') &&
    resp.url().includes('SortBy=createdAt') &&
    resp.url().includes('SortDescending=true'),
  { timeout: 10_000 },
);
```

Every Page Object for a DevExtreme DataGrid **must** extend `DxGridPage`. The base class

```typescript
// ✅ Inherited from DxGridPage — no need to implement in your POM
await companiesPage.goto();
await companiesPage.waitForGridLoad();   // ← always wait before interacting with rows
```

## CRUD test pattern — serial end-to-end

CRUD tests **must** be declared with `test.describe.serial` so they run in dependency order.
Each step builds on the state left by the previous step.

### Unique names — collision-free

All test data names **must** be unique per suite run using `Date.now()`:

```typescript
const uniqueName = `E2E-Cmp-${Date.now()}`;  // e.g. "E2E-Cmp-1776259948992"
const updatedName = `E2E-Upd-${Date.now()}`;
```

- Prefixes (`E2E-Cmp-`, `E2E-Upd-`, `E2E-AuditFlow-`) make leftover test data recognisable
  in the database and easy to bulk-clean.

### Finding the just-created row with `sortCreatedDesc()`

The grid may contain many rows. After creating or updating, call `sortCreatedDesc()` so
the freshly mutated row is always at position 0, regardless of how many other rows exist:

```typescript
await companiesPage.waitForGridLoad();
await companiesPage.sortCreatedDesc();
await expect(companiesPage.rowByName(uniqueName)).toBeVisible({ timeout: 10_000 });
```

### Asserting the HTTP response status

Always assert the response status in CRUD tests — do not assume the action succeeded
from UI feedback alone:

```typescript
const [createResponse] = await Promise.all([
  page.waitForResponse((resp) =>
    resp.url().includes('/api/companies') &&
    resp.request().method() === 'POST' &&
    resp.status() === 201,
  ),
  companiesPage.fillAndSubmit(uniqueName),
]);
expect(createResponse.ok()).toBe(true);
```

### Example: full serial CRUD describe block

```typescript
test.describe.serial('CRUD — real backend', () => {
  const uniqueName = `E2E-Cmp-${Date.now()}`;
  const updatedName = `E2E-Upd-${Date.now()}`;

  test('creates ...', async ({ page }) => { /* POST → 201 */ });
  test('edits ...',   async ({ page }) => { /* PUT  → 200 */ });
  test('deletes ...', async ({ page }) => { /* DELETE → 204 */ });
});
```

## DevExtreme DataGrid quirks

### Row-level actions: always use `[title="..."]` with `{ force: true }`

DX renders button `hint` values as the DOM `title` attribute, **not** `aria-label`.
`getByRole('button', { name: '...' })` will time out on actionability checks because a DX
tooltip overlay from an adjacent button can obscure the target:

```typescript
// VIOLATION: DX hint is title, not aria-label
await row.getByRole('button', { name: 'Delete' }).click();

// ✅ Correct
async clickDelete(name: string): Promise<void> {
  const row = this.rowByName(name);
  await row.hover();
  await row.locator('[title="Delete"]').click({ force: true });
}
```

### SearchPanel: `fill()` is safe for mock tests; do not use for CRUD

The DX SearchPanel debounces user input via an internal timer before it fires a grid
reload. `fill()` dispatches an input event that DX processes, but the debounce means
the reload may arrive slightly after `fill()` resolves. Always wait for the grid to settle:

```typescript
await companiesPage.searchInput.fill('Acme');
await expect(companiesPage.dataRows).toHaveCount(1, { timeout: 5000 });
```

**Do not use search to locate a row in CRUD tests.**  Use `sortCreatedDesc()` instead —
it is deterministic and does not depend on debounce timing or query handling.

### Column sort: three-state cycling (no sort → ASC → DESC → no sort)

DX column headers cycle through three states. To reach DESC from an unknown initial state,
always click **twice** and gate each click on its response:

```typescript
// First click → ASC
await createdHeader.click();
await page.waitForResponse(
  (resp) => resp.url().includes('SortBy=createdAt'),
  { timeout: 10_000 },
);
// Second click → DESC
await createdHeader.click();
await page.waitForResponse(
  (resp) =>
    resp.url().includes('SortBy=createdAt') && resp.url().includes('SortDescending=true'),
  { timeout: 10_000 },
);
```

### Confirm dialog: `.dx-popup-wrapper` filtered by button

DX renders its `confirm()` dialog as a `.dx-popup-wrapper`. It is **not**
`.dx-overlay-content.dx-dialog`. Use the scoped filter approach to distinguish it from
the form popup:

```typescript
// VIOLATION: wrong selector
page.locator('.dx-overlay-content.dx-dialog');

// ✅ Correct
get confirmDialog(): Locator {
  return this.page.locator('.dx-popup-wrapper').filter({
    has: this.page.getByRole('button', { name: /^yes$/i }),
  });
}

async confirmDelete(): Promise<void> {
  await this.page.getByRole('button', { name: /^yes$/i }).click();
}
```

### Form popup: `pressSequentially` over `fill()`

DX `TextBox` defaults to `valueChangeEvent: "change"`, which means programmatic `fill()`
does not fire the change event that updates react-hook-form state. Use `Ctrl+A` to select
all existing text, then `pressSequentially` to dispatch real keyboard events:

```typescript
async fillAndSubmit(name: string): Promise<void> {
  await this.nameInput.press('Control+a');
  await this.nameInput.pressSequentially(name);
  await this.submitButton.click();  // blur → change → DX onValueChanged → RHF update
}
```

### Form popup scoping: filter by a unique child element

When a page can have both a **form popup** and a **confirm dialog** (both `.dx-popup-wrapper`),
scope the form popup locator to a unique input it contains:

```typescript
// ✅ Scoped to the popup that contains the company-name input
this.popup = page.locator('.dx-popup-wrapper').filter({
  has: page.locator('#company-name'),
});
```

### Column headers locator

```typescript
// ✅ Targets the text nodes inside the DX header row
this.columnHeaders = this.grid.locator('.dx-datagrid-headers .dx-datagrid-text-content');
```

### Data rows locator

```typescript
// ✅ Only real data rows, not header/group/summary rows
this.dataRows = this.grid.locator('.dx-data-row');
```

### Finding a row by name

`filter({ hasText: name })` performs a substring match on all text content within the row.
This works even when a column is visually truncated — DX keeps the full text in the DOM:

```typescript
rowByName(name: string): Locator {
  return this.dataRows.filter({ hasText: name });
}
```

## Test isolation and cleanup

- **Never hardcode `id` values** from a previous test run — `id` is not predictable.
  Capture the `id` from the create response and thread it through later steps:

```typescript
// Step 1 — capture created ID
const body = await createResponse.json();
companyId = body.id as string;

// Step 4 — use captured ID to filter audit logs
```

- **Test data is not automatically cleaned up between runs.** Leftover `E2E-*` rows in
  the database are expected and do not cause test failures because `sortCreatedDesc()`
  always finds the row created in the current run.
- **Never share state between `test.describe` blocks via module-level variables** — use
  variables declared inside the `describe` block.

---

## Parallel execution — file-level, and every spec file must stay independent

Both configs run with `workers: '50%'` and `fullyParallel` **off**. That means:

- **Spec files run in parallel** on separate workers; tests **within** a file keep their
  order on one worker, so `test.describe.serial` CRUD chains are unaffected.
- **Never set `fullyParallel: true`** — it would split a file's tests across workers and
  break the serial CRUD pattern.
- **Every spec file must be runnable concurrently with every other spec file.** The
  existing rules already guarantee this; they are now load-bearing:
  - mocked specs intercept routes on their own `page` only;
  - auth is the shared read-only storageState (`loginAsAdmin` just navigates);
  - real-backend CRUD files use unique names with a **file-distinct prefix**
    (`E2E-Cmp-`, `E2E-AuditFlow-`, `E2E-Homework-`, …) so two workers starting in the
    same millisecond can never collide. A new CRUD spec file **must** pick a prefix no
    other file uses.
- **Never write a spec that mutates global backend state** another spec reads (feature
  flags, the seeded dev admin, the seed club). If a flow genuinely needs that, isolate it
  and flag it in review — it needs its own serial project, not a silent dependency.

## Auth in beforeEach

Every `beforeEach` for an authenticated spec **must** use `loginAsAdmin` from
`playwright/utils/auth.ts`. Never inline the login ceremony in each spec file.

```typescript
import { loginAsAdmin } from '../../../playwright/utils/auth';

test.beforeEach(async ({ page }) => {
  await loginAsAdmin(page);
  companiesPage = new CompaniesPage(page);
});
```

Credentials come from `.env.e2e` via `process.env.E2E_ADMIN_EMAIL` / `E2E_ADMIN_PASSWORD`.
They are exported from `auth.ts` as `E2E_EMAIL` and `E2E_PASSWORD` for the rare cases where
a spec needs the values directly (e.g. the login.spec.ts auth flow test). Never hardcode
credentials in spec files.

## Cross-feature integration tests

When a feature writes data that another feature should display (e.g. Company CRUD + Audit
Log), put the flow in a dedicated `<feature>-<other-feature>.spec.ts` file as a single
`test.describe.serial` suite. Capture IDs from early step responses and use them in later
steps for precision filtering:

```typescript
// Captured in Step 1, used in Step 4
let companyId: string | undefined;

// Step 1
const body = await createResponse.json();
companyId = body.id as string;

// Step 4 — filter audit logs by company ID so no false positives from other test runs
await auditLogsPage.filterByEntityId(companyId!);
```

## What to test in a full feature E2E suite

Each feature's E2E suite **must** cover all of the following categories. Missing categories
are treated as incomplete coverage:

| Category | Required tests |
|---|---|
| **Page rendering** | Container visible, heading, key UI elements (buttons, grid) |
| **Grid columns** | Expected column headers rendered (mock empty data) |
| **Search / filter** | Correct API called with filter param; grid updates (mocked) |
| **Column sorting** | Each sortable column sends correct `SortBy` + `SortDescending` params |
| **Pagination** | Pager visible when totalCount > pageSize; clicking Next sends `Page=2` |
| **CRUD — real backend** | Serial: create → edit → delete; each step asserts the HTTP status AND grid state |

## Running E2E tests

```bash
# Affected specs only — maps the branch diff to spec files. Run this before pushing.
npm run e2e:affected

# Full suite (ephemeral Postgres + migrator + isolated WebApi + both servers)
npm run e2e

# Stop the E2E containers (runs leave them up by default so the next run is warm)
npm run e2e:down

# A single spec file
cd e2e && npx playwright test tests/web/clubs/clubs.spec.ts

# A subset by grep
cd e2e && npx playwright test tests/web/clubs/ --grep "CRUD"

# Expo specs against a Metro dev server you already have running (fast iteration)
npm run dev:expo   # in another terminal
cd e2e && npx playwright test --config playwright.expo-local.config.ts tests/expo/auth

# With the Playwright UI (interactive)
cd e2e && npx playwright test --ui
```

`npm run e2e` starts the ephemeral Postgres, runs the migrator, builds and starts the
isolated WebApi on `:5003`, and runs the suite. Containers are **left running by default**
so the next run reuses them and skips both the image rebuild and the migration — the
difference between a ~5-minute cold start and a ~30-second warm one. That warm path is
what makes `e2e:affected` fast enough to run before every push. Stop the containers with
`npm run e2e:down`, or set `E2E_TEARDOWN=1` on a run to tear down afterwards.

**`e2e:affected` does not use your dev server for the expo specs.** It builds a static
`expo export` (~50s) and serves that itself, mirroring the CI job. Two reasons, both learned
the hard way:

- A dev-mode Metro loads `.env.development.local`, so *your* local overrides decided which UI
  the bundle contained. A run could disagree with CI about whether a feature-flagged screen
  even exists.
- On-demand bundling per navigation is slow, and across a couple of dozen specs Metro died
  mid-run — every remaining spec then failed with `ERR_CONNECTION_REFUSED`.

The build is one fixed cost regardless of how many specs run, so this gets relatively cheaper
as the suite grows. If a dev server already owns `:8081`, the runner serves on `:8091` instead
and passes the origin through `E2E_EXPO_BASE_URL` rather than fighting it.

Backend must be running before tests that hit the real API. `npm run e2e` supplies its own
isolated backend; a bare `npx playwright test` does not (`npm run dev:backend`).

### `E2E_SERVERS` — which dev server Playwright starts

`playwright.config.ts` starts the Next.js dev server **and** Metro by default, because
Playwright boots every entry in `webServer` regardless of which project is selected.
`E2E_SERVERS` narrows that so a web-only run does not pay for Metro:

| Value | Starts |
|---|---|
| `both` (default) | Next.js `:3000` + Metro `:8081` |
| `web` | Next.js `:3000` only |
| `expo` | Metro `:8081` only |

`e2e:affected` sets this automatically from the selected specs. Both entries keep
`reuseExistingServer: true`, so an already-running server is always reused.

### The shared-database guard

`reuseExistingServer: true` has a sharp edge: the `NEXT_PUBLIC_API_URL=http://localhost:5003`
override in `playwright.config.ts` only applies to a server **Playwright starts itself**. A
dev server already listening on `:3000` was started from `apps/web/.env.local`, which points
at `:5002` — the main stack, backed by the **hosted** dev database. Running the real-backend
CRUD specs against that would create, edit and delete rows in shared data.

So `e2e:affected` refuses to run web specs when something is already serving `:3000`. Stop
your dev server and re-run. `E2E_ALLOW_SHARED_BACKEND=1` overrides the guard — only use it
if you are certain the running server already targets `:5003`.

A bare `npm run e2e` does **not** have this guard; it is inherited behaviour and the reason
the guard exists in the wrapper. Prefer `npm run e2e:affected`.

### Machine-readable selection

`npm run e2e:affected -- --json` prints the selection and runs nothing:

```json
{ "base": "origin/dev", "specs": [], "web": [], "expo": [], "projects": [], "uncovered": [] }
```

`e2e-post-merge.yml` consumes this to decide which jobs to run. Use `--dry-run` for the
human-readable version.

## Affected-spec selection — `e2e/scripts/affected-specs.mjs`

The change → spec mapping is a single declarative table, imported by both the local runner
(`e2e/scripts/e2e-affected.mjs`) and the CI attestation gate
(`scripts/check-e2e-attestation.mjs`) so the two can never disagree about what a diff is
expected to cover.

### Rules

- **Rules are unioned, not first-match.** A diff touching one feature plus a shared package
  selects both sets of specs.
- **A changed path that matches no rule is reported as `uncovered`** — it never inflates the
  run to the whole suite. A slow gate is a gate nobody runs; an honest coverage gap is
  actionable.
- **A rule may map to `specs: []`** to record *deliberately* uncovered ground (Maestro-only
  features, the mobile API the synthetic-auth Expo suite never calls). Always give the
  reason in `why`. This is how "we know, and it's fine" is distinguished from "unmapped".
- **Adding a spec directory, a web feature, or a backend module means updating the table.**
  A new feature with no rule silently gets no pre-push coverage.

## Pre-push attestation

E2E is not a required CI check — the full suite is too expensive to run per PR. Instead the
**claim** that it ran is enforced, and the claim is bound to the commit it was run against.

On a passing run, `e2e:affected` prints a paste-ready attestation line:

```text
e2e: sha=<40-hex> result=passed specs=<n> at=<iso8601>
```

Paste it into the `## E2E` section of the PR. The `E2E Attestation` check
(`.github/workflows/e2e-attestation.yml`, required on PRs into `dev`) runs no tests — it
verifies that:

| Rule | Why |
|---|---|
| `sha` equals the PR head SHA | a stale line from an earlier commit cannot be reused |
| `at` is later than the head commit's committer date | the run happened *after* the code it claims to cover |
| `at` is not in the future | clock-fudging is visible |
| `result=passed` | a failing run is not an attestation |

Every new push turns the check red until the line is regenerated. The check skips entirely
when the diff selects no specs, so docs-only and backend-only-uncovered PRs are unaffected.

The runner only emits the line when the e2e-relevant paths in the working tree are **clean** —
a receipt for a dirty tree would attest to code nobody can review. Commit first, then run.

`e2e/.e2e-receipt.json` (gitignored) holds the full machine-readable receipt of the last run:
head SHA, working-tree digest, selected specs, projects, result, timings.

### Escape hatch

Label the PR `skip-e2e`. The check passes with a loud annotation, and GitHub records who
applied the label. Deliberate and attributable — which is the whole point.

## The pre-push receipt gate

`.husky/pre-push` runs `scripts/check-e2e-receipt.mjs`, which reads the refs being pushed,
maps the pushed diff to specs, and — when specs are selected — requires
`e2e/.e2e-receipt.json` to show a passing run that matches what is being pushed:

| Rule | Why |
|---|---|
| receipt exists | nothing to verify otherwise |
| `result: passed` | a failing run is not a pass |
| `headSha` equals the pushed `HEAD` | the run must describe the code being pushed |
| `dirty` is empty | a run over an uncommitted tree describes no pushed commit |
| `finishedAt` within 24h | a week-old receipt is not evidence about today |
| recorded specs cover the selected set | running a superset is fine; a subset is not |

Skip deliberately with `E2E_SKIP="reason" git push`. It says so loudly and the PR still
needs a valid attestation to merge.

**This gate is bypassable and that is understood.** `git push --no-verify` skips every
hook and nothing client-side can prevent it. Its job is to turn *"I forgot"* into
*"I chose to skip"*. The unbypassable half is the required `E2E Attestation` check on the
PR, which is bound to the head SHA and cannot be satisfied from a developer's machine.

## Post-merge run on `dev`

`.github/workflows/e2e-post-merge.yml` runs the affected specs after a merge lands on
`dev`, and on failure opens a Linear ticket **assigned to the merge author** (not to
whoever last touched the spec — the spec is usually innocent). So skipping locally has a
visible, attributable cost without paying for E2E on every PR.

Cost shape: only selected specs run; the Docker/Key Vault/WebApi job runs only when web
specs are selected, so expo-only merges take about a minute; nothing runs when the merge
selects no specs. Runs queue rather than cancel, because cancelling would destroy the
per-merge attribution the workflow exists to provide.

`report-failures.ts` takes ownership from `E2E_BLAME_EMAIL` when set, falling back to
spec-file `git blame` (the weekly sweep case), then to `E2E_FALLBACK_ASSIGNEE`.
